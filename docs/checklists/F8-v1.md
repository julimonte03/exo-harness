# Checklist F8: v1.0 (criterios 1 a 4 y release)

Verifica con agentes reales y con el instalador remoto lo que la v1.0 promete: instalar y adoptar en menos de 2 minutos, sumar un segundo agente sin romper el primero, ciclos Tier 1 y Tier 3 válidos, y la ingeniería inversa a escala. Al final están los pasos del release que hace el dueño.

**Aislamiento en todas las corridas:** `EXO_DATA_DIR` y `EXO_MEMORY_DB` apuntan a una carpeta temporal, nunca a la del usuario. Copilot CLI corre con su propio `COPILOT_HOME` (`tests/_agents.py`), y git, con `GIT_CONFIG_GLOBAL` aislado.

## Criterio 1: instalar y adoptar en menos de 2 minutos (2026-11-24, Windows 11, PowerShell 5.1)

**Preparación:**
1. Un repo de prueba con un `README.md` y un commit.
2. El instalador remoto real, desde GitHub:
   ```powershell
   $env:EXO_REF = 'feat/F8-v1'; $env:EXO_INSTALL_NO_PATH = '1'
   & ([scriptblock]::Create((irm https://raw.githubusercontent.com/julimonte03/exo-harness/feat/F8-v1/install.ps1)))
   ```
3. Las herramientas de uv (`UV_TOOL_DIR`, `UV_TOOL_BIN_DIR`) y la carpeta de datos van a carpetas temporales.
4. Después, `exo init --project <repo> --agents <agente> --yes`, sin editar nada a mano.

**Qué se mide:** el reloj corre desde que se baja el instalador hasta que termina `exo init`. Al final, `exo doctor --json`.

| Agente | Modo | Instalar | Instalar y adoptar | `exo doctor` |
|---|---|---|---|---|
| Claude Code | uv | 51,1 s | **56,4 s** | sin errores |
| GitHub Copilot | uv (con caché) | 22,0 s | **27,9 s** | sin errores |
| Claude Code | sin uv (venv y pip desde git) | 61,6 s | **67,1 s** | sin errores |

En cada repo adoptado, el agente ve las skills del proyecto y corre el `exo` recién instalado (`exo skills list --json`):
- Claude Code ve 57 skills (las 38 del proyecto más las suyas);
- Copilot ve las 38 del proyecto y 3 propias.

**Lo que encontró:** con la salida redirigida (`*> install.log`), `install.ps1` cortaba en el modo uv. PowerShell 5.1 convierte el progreso que uv escribe en stderr en un error, y el `Stop` del script lo hacía terminar. Arreglado en `2086ba4`, con test.

**Por qué el Tier 3 de Copilot quedó parcial:**
1. **El verify quedó `blocked`, con razón:** un riesgo de exposición por los permisos del archivo de la base necesitaba la aceptación del `tech_lead`, y en una corrida desatendida no hay quién la dé.
2. **Copilot CLI 1.0.114 con `-p` deniega sin preguntar lo que no es un comando simple,** aunque estén permitidos `shell(exo:*)` y `shell(git:*)`:
   - las cadenas con `;`;
   - `git --no-pager <subcomando>`, también con `shell(git --no-pager:*)`;
   - `git diff ... main...HEAD`, porque toma el `...` como una ruta;
   - los scripts de PowerShell con variables.
3. **La cuenta de Copilot se quedó sin cuota mensual** antes de la última reanudación, que llevaba la decisión del `tech_lead`.

El dueño decidió cerrar F8 con esta evidencia (2026-11-25).

**Lo que las corridas mostraron del contenido (corregido en F8):**
- **Copilot sin shell en los subagentes** (`59294c9`): en Copilot CLI sobre Windows, un custom agent con `tools: … Bash` no tiene shell, aunque la documentación de GitHub dice que `Bash` es alias de `execute`. Lo verifiqué con dos agentes de prueba. `sdd-implementer` y `sdd-verifier` declaran también `PowerShell`, y `exo validate` lo exige.
- **El retrabajo no convergía** (`8d15cf9`): en modo automático, el agente arreglaba cada hallazgo de los jueces, y los jueces volvían a revisar todo el diff en cada ronda. Ahora:
  - se decide por severidad: Critical y High vuelven a apply, y Medium y Low se aplazan a un followup, registrados como decididos (`dismissed_followups`, con el motivo "deferred to a followup (automatic mode)"), y `pr.md` los lista en "Known followups";
  - el re-verify revisa el arreglo;
  - hay a lo sumo dos rondas de retrabajo, y en la siguiente se detiene y le pregunta a la persona. Una ronda es cada vuelta de verify a apply, por el veredicto o por un hallazgo Critical o High de un juez.
- **Runner de Copilot** (`d07b207`, `a267aa0`): apaga el pager y avisa en el pedido qué comandos aprueba el matcher.

## Release v1.0.0 (lo hace el dueño, con su OK)

**Cómo se cierra una fase desde F8** (decisión del dueño, 2026-11-25): con un PR de la rama de la fase a `main`, que el dueño abre y mergea en GitHub con la CI verde. Nunca hay push directo a `main`, tampoco del dueño.

**Una vez, en GitHub** (Settings del repo):
1. **Rules > Rulesets > New branch ruleset**, sobre `main`, **sin bypass** (ni tu usuario):
   - "Restrict deletions" y "Block force pushes";
   - "Require a pull request before merging";
   - "Require status checks to pass", con los jobs de `ci.yml`, para que un PR no se mergee con la CI en rojo.
2. **Rules > Rulesets > New tag ruleset**, sobre `v*`: "Restrict creations", "Restrict updates", "Restrict deletions" y "Block force pushes", con tu usuario como único bypass. Así nadie mueve un tag publicado (threat model, TM-5).
3. **General > Releases:** activá la inmutabilidad de los releases si tu cuenta la ofrece, para que un asset publicado no se pueda reemplazar (TM-4).
4. **Environments:**
   - `pypi`, con "Required reviewers" (vos) y "Deployment branches and tags" limitado al patrón de tags `v*`;
   - `testpypi`, sin reglas.

**Una vez, en PyPI y TestPyPI:**
5. En https://pypi.org/manage/account/publishing/, "Add a new pending publisher": PyPI Project Name `exo-harness`, Owner `julimonte03`, Repository name `exo-harness`, Workflow name `release.yml`, Environment name `pypi`.
6. Lo mismo en https://test.pypi.org/manage/account/publishing/, con Environment name `testpypi`.

**En cada release:**
7. **La versión**, en la rama de la fase y antes del PR. Para la v1.0.0 ya está hecho: `_meta.VERSION` pasó a 1.0.0 en `4b8a5d3` y la sección del CHANGELOG tiene fecha (2026-11-25). Para las próximas:
   - `VERSION` en `src/exo/_meta.py`;
   - la fecha de su sección en `CHANGELOG.md` (`## [X.Y.Z] - AAAA-MM-DD`): las notas del release salen de ahí;
   - reinstalar el editable (`pip install -e ".[dev]"`), porque `test_meta` compara la versión instalada con `_meta.VERSION`;
   - regenerar los goldens con `pytest --update-golden` y revisar el diff (solo cambia la versión);
   - el PR a `main`, que mergeás con la CI verde.
8. **Ensayo:** Actions > Release > Run workflow, sobre `main`. Corre los tests, arma, verifica y publica en TestPyPI, sin release de GitHub.
9. **El tag**, sobre `main` actualizado, después del merge:
   ```sh
   git switch main
   git pull --ff-only
   git tag -a v1.0.0 -m "exo 1.0.0"
   git push origin v1.0.0
   ```
   `release.yml` corre los tests, verifica que el tag coincida con `_meta.VERSION`, arma el wheel y el sdist, escribe `SHA256SUMS`, crea el release de GitHub y publica en PyPI cuando apruebes el environment `pypi`.
10. **Verificación:** `uvx --from exo-harness exo --version`, y el instalador remoto sin `EXO_REF`, que toma el último release y verifica el wheel contra su `SHA256SUMS`.
